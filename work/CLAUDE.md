# 案件作業ディレクトリ

サブエージェント間の**中間成果物の受け渡し場所**。
エージェントは互いを呼べず毎回コンテキストゼロで起動するため、**連携はすべてこのディレクトリのファイル経由**で行う。

---

## 1. ディレクトリ構造

```
work/<案件ID>/                案件ID = <施行日YYYYMMDD>_<規程名>
├── 00_要件定義.md            00-intake
├── 01_法令調査.md            01-legal-research
├── 02_整合性分析.md          02-consistency
├── 03_素案.md                03-drafter
├── 04_リーガルチェック.md    04-legal-review
├── 05_反対意見.md            05-devils-advocate
├── 06_最終案.md              06-finalizer  ← 人間承認ゲートの対象
├── 07_周知資料.md            07-comms
├── 09_手続き判定.md          09-procedure
├── 10_新旧対照表.md          10-diff-impact
├── audit.md                  全エージェントが追記
└── out/                      docx/pptx/xlsx の完成品
```

案件IDは施行日確定まで仮IDで作業し、`00-intake` 完了後に確定IDへリネームする。

---

## 2. 入出力の対応表

**このマトリクスが崩れるとパイプラインが壊れる。** エージェントを変更するときは必ずここを確認する。

| エージェント | 読む | 書く |
|---|---|---|
| `00-intake` | ルート CLAUDE.md, registry/ | `00_要件定義.md`, `audit.md` |
| `01-legal-research` | `00` | `01_法令調査.md` |
| `02-consistency` | `00`, registry/ | `02_整合性分析.md` |
| `03-drafter` | `00`, `01`, `02`, templates/ | `03_素案.md` |
| `04-legal-review` | `00`, `01`, `02`, `03` | `04_リーガルチェック.md` |
| `05-devils-advocate` | `00`, `03` | `05_反対意見.md` |
| `06-finalizer` | `00`〜`05` すべて | `06_最終案.md` |
| `09-procedure` | `00`, `04`, `06`, registry/ | `09_手続き判定.md` |
| `10-diff-impact` | `00`, `02`, `06`, registry/, templates/ | `10_新旧対照表.md`, `out/05_新旧対照表.xlsx` |
| `07-comms` | `00`, `05`, `06`, `09`, `10`, templates/ | `07_周知資料.md`, `out/01,02,03,06` |

`08-registry` はこのディレクトリを使わない（`registry/` に書く）。

## 3. 成果物のヘッダ（必須）

各エージェントは成果物の冒頭に必ず置く。**これがないと、後続が何を入力に作られたか追えない。**

```markdown
---
案件ID: 20260810_生成AI利用規程
作成エージェント: 03-drafter
作成日: 2026-08-10
入力: work/20260810_生成AI利用規程/00_要件定義.md, 01_法令調査.md, 02_整合性分析.md
---
```

---

## 4. `audit.md`

**全エージェントが追記する根拠ログ。上書きしない。**

労基署対応・監査対応で「この条文はどの法令・どの既存規程を根拠に作られたか」を示すために使う。

記録するもの：

| エージェント | 記録内容 |
|---|---|
| `00-intake` | ヒアリングで得た事実の出所（ユーザー発言 / 既存規程） |
| `01-legal-research` | 確認した法令の URL と確認日 |
| `02-consistency` | 参照した規程ファイルの webUrl と最終更新日 |
| `03-drafter` | 各条文の根拠 |
| `04-legal-review` | 参照した法令・裁判例の URL と確認日 |
| `06-finalizer` | 調停の判断理由 |
| `09-procedure` | 参照した社内文書と根拠条項 |

## 5. `out/` — 完成品

```
out/01_〇〇規程概要資料.docx   経営層・稟議用
out/02_〇〇規程スライド.pptx   説明会用
out/03_主な改正点.docx         全社員向け（です・ます調）
out/04_〇〇規程.docx           規程本体
out/05_新旧対照表.xlsx         改定時のみ
out/06_FAQ.docx                想定問答
```

**OneDrive へアップロードするのは `out/` の中身のみ。**
`work/<案件ID>/` 直下の中間成果物（`00`〜`10`, `audit.md`）は**絶対にアップロードしない**。

アップロード先：`REG_ROOT/<施行日YYYYMMDD>_<規程名>/`
（既存の `20260401_人事評価規定/` の構成に準拠）

---

## 6. 承認ゲート

`06_最終案.md` が人間の承認対象。**承認前に以下をしてはならない。**

- `07-comms` を実行して周知資料を作る（未承認の内容が出回る）
- `out/` に完成品を生成する
- OneDrive にアップロードする

承認は `/規程-新規` `/規程-改定` の親コマンドが `AskUserQuestion` で取る。

---

## 7. 案件の完了後

- `work/<案件ID>/` は**削除せずコミットして残す**。改定時に前回の判断根拠を追える
- `audit.md` の完全性を確認してからコミットする
- 案件が中止になった場合も残す。`00_要件定義.md` に中止した旨と理由を追記する

---

## 8. やってはいけないこと

- エージェントの出力先を勝手に変える（第2節のマトリクスが崩れる）
- 成果物のヘッダを省略する
- `audit.md` を上書きする（追記のみ）
- 中間成果物を OneDrive にアップロードする
- 承認前に `out/` を生成する
- 案件ディレクトリを削除する

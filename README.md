# 社内規程 作成・改定支援システム

株式会社エバーグリーンモビリティ 総務人事課向け。Claude Code のサブエージェント機能で、
社内規程の制定・改定を「調査 → 素案 → 検証 → 最終案 → 周知資料」まで一気通貫で行う。

ナレッジは OneDrive 上の現行規程（Microsoft 365 コネクタ経由で読み取り）。

---

/規程-台帳更新                                  # 最初に1回：現行規程を棚卸し

## パイプライン

**新規制定**
```
⓪要件 → ⑧台帳 → ①法令 ‖ ②整合 → ③素案 → ④法務 ‖ ⑤反対 → ⑥最終案
  → 【人間の承認】 → ⑨手続き → ⑩影響範囲 → ⑦周知資料 → docx/pptx/xlsx → OneDrive
```

**改定**
```
⑧台帳（現行版確定）→ ⓪要件 → ②整合 ‖ ①法令 → ③差分ドラフト → ④法務 ‖ ⑤反対
  → ⑥最終案 → 【人間の承認】 → ⑩新旧対照表 → ⑨手続き → ⑦周知資料 → OneDrive
```

`‖` は並列実行。**サブエージェントは互いを呼べない**ため、スラッシュコマンド（親）が順に呼び、
成果物は `work/<案件ID>/NN_*.md` のファイル経由で受け渡す。

## 設計上の要点

### 1. 承認ゲート

⑥最終案の後に**人間の承認**を必ず挟む。承認前に周知資料を作らず、OneDrive にアップロードしない。
⑥が確定できなかった論点は「経営判断事項」として人間に上げる。AI が決着させない。

### 2. 現行版の確定が先

OneDrive には同名規程の複数版が併存しており、**現行版が機械的に判別できない**
（コンプライアンス管理規程、整備管理規程、ハラスメント防止規程 ほか）。
⑧が台帳化し、判別できないものは `status: 要確認` として人間の確認を仰ぐ。
**推測でどれかを現行版に決めない。**

### 3. 規程の2階層構造

D&Dホールディングスの**グループ規程**（上位規範）と EVGM の**自社規程**が併存する。
②は横（自社規程間）だけでなく**縦（グループ規程との上下関係）**も検証する。
HD層の規程は EVGM 単独で制定・改廃できないため、⓪が判定して早期に警告する。

### 4. 手続きの瑕疵を防ぐ

規程が無効になる原因の多くは条文ではなく手続き。⑨が就業規則該当性（労基法89条）を判定し、
該当する場合は意見聴取（90条）・労基署届出（89条）・周知（106条）を必須手続きとして提示する。
決裁ルートは個別決裁基準表・稟議規程・取締役会規程を**実際に読んで**判定する。

### 5. ハルシネーション対策

- 法令の条番号は e-Gov で **WebFetch して確認**したもののみ条文に使う。未確認は `【要確認】` で別掲
- 既存規程は `read_resource` で**本文を読んでから**引用する。検索スニペットで引用しない
- ③の全条文に根拠を紐づける（`03_素案.md` 第2節の根拠対応表に空欄があってはならない）
- 全エージェントが `work/<案件ID>/audit.md` に根拠と出所を追記する

### 6. 秘匿情報の保護

①は外部検索を行うが、**現行規程の本文を検索クエリに含めない**。一般的な法令名・制度名のみで検索する。

## team アカウントへの移行

実運用は本アカウント（`takizawa-d@evgm.co.jp`）ではなく team アカウントで行う。

1. team アカウントで Microsoft 365 コネクタを接続する
2. `CLAUDE.md` 第1節「格納先」の表を team 環境の値に書き換える
   （エージェント定義にパスをハードコードしていないため、**ここ1箇所で済む**）
3. `REG_ROOT` を正本置き場（`share@evgm.co.jp` 配下）に設定する

`REG_ROOT_PERSONAL`（個人領域）は読み取り専用。書き込みは `REG_ROOT` のみ。

## 運用上の注意

- **⑧の棚卸しは四半期に1回**、および改定着手前に実行する
- 台帳で人間が確定した項目には `last_verified_by: human` が付き、⑧は上書きしない
- OneDrive 上の既存ファイルの**削除・リネーム・移動は行わない**（提案のみ）
- 改定時、旧版ファイルは削除せず履歴として残す（効力は附則の廃止条項で処理する）

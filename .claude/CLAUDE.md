# Claude Code 設定ディレクトリ

`agents/`（サブエージェント11本）と `commands/`（スラッシュコマンド3本）の**定義を書き換えるときのルール**。
ルートの `CLAUDE.md`（格納先・2階層構造・体裁ルール・禁止事項）が上位ルール。矛盾する定義を書かない。

> **注意：`agents/` と `commands/` の直下に `CLAUDE.md` を置いてはならない。**
> これらのディレクトリの `.md` はすべてエージェント／スラッシュコマンドとして自動登録されるため、
> `CLAUDE.md` を置くと「CLAUDE」という名前のエージェントやコマンドができてしまう。
> 両ディレクトリ向けのルールは、このファイル1本にまとめている。

# 第1部　サブエージェント（`agents/`）

## 1. サブエージェントの制約（設計の前提）

| 制約 | 意味すること |
|---|---|
| **エージェント同士は互いを呼べない** | 連携は必ずファイル経由。定義に「〇〇エージェントを呼ぶ」と書かない |
| **毎回コンテキストゼロで起動する** | 会話履歴を引き継がない。必要な情報は「事前に読むもの」に列挙し、本人に読ませる |
| **親（スラッシュコマンド）が順番を制御する** | 実行順の記述は `commands/` 側の責務。エージェント側に書かない |
| **戻り値は要約されて親に返る** | 成果物は必ずファイルに書く。返答文だけで完結させない |

## 2. ファイル形式

```markdown
---
name: NN-agent-name          # 英小文字ケバブケース。ファイル名と一致させる
description: 何をするエージェントか。親が「いつ呼ぶか」を判断できる粒度で書く
tools: Read, Write, ...      # 最小権限で列挙
model: sonnet | opus
---

# エージェント名（日本語）
```

### 本文の標準構成

この構成を崩さない。エージェント間で揃っていないと保守できなくなる。

```
# 見出し（このエージェントの立ち位置を1〜2行で）

## 目的            → どのファイルを作るのかを1行で
## 事前に読むもの  → 必読ファイルを漏れなく列挙。ルート CLAUDE.md は全エージェント必読
## （固有の観点・手順）→ チェック観点は表に、手順は番号付きに
## 出力            → 出力先のパスと成果物の見出し構成をコードブロックで示す
                     audit.md への追記内容も書く
## やってはいけないこと → 具体的な失敗パターンを列挙。「注意する」ではなく「〜しない」
```

## 3. tools は最小権限で

**全エージェントに `*` を与えない。権限の切り分け自体が安全設計になっている。**

| 分類 | 対象 | 与える権限 | 理由 |
|---|---|---|---|
| 条文を書く役 | `03-drafter`, `06-finalizer` | **外部アクセスなし**（Read/Write/Edit/Glob/Grep） | 規程本文を扱うため情報流出経路を作らない |
| 外部調査専任 | `01-legal-research`, `04-legal-review` | WebSearch/WebFetch。**社内文書ツールは与えない** | 現行規程を外部検索クエリに混ぜる事故を構造的に防ぐ |
| 社内文書を読む役 | `02`, `08`, `09`, `10` | `sharepoint_search` / `sharepoint_folder_search` / `read_resource` | **読み取り専用。upload/delete/move は与えない** |
| 対話する役 | `00-intake` | `AskUserQuestion` | ユーザーに直接質問する唯一のエージェント |
| 文書生成する役 | `07-comms`, `10-diff-impact` | `Skill`（docx/pptx/xlsx） | 完成品の生成 |

**アップロード権限（`sharepoint_upload_file`）はどのエージェントにも与えない。**
OneDrive への書き込みは親コマンドがユーザー確認を取ってから行う。

## 4. model の選び方

| model | 対象 | 判断基準 |
|---|---|---|
| `opus` | `03`, `04`, `05`, `06` | 条文を書く・法的判断をする・対立を調停する＝**誤ると規程が無効になる役** |
| `sonnet` | `00`, `01`, `02`, `07`, `08`, `09`, `10` | 収集・整理・照合・定型文書生成が主体 |

## 5. 番号の意味

`NN-` はパイプライン上の標準的な実行順。`00`〜`07` が当初設計の主系列、
`08`〜`10` が後から追加した支援系（`08` は `02` の前提、`09` `10` は承認後）。

**既存の番号を振り直さない**（コマンド側の参照が壊れる）。追加は `11-` 以降か `02b-` の枝番。

## 6. 全エージェント共通で守らせること

定義を書くとき、以下が本文に反映されているか確認する。

1. 成果物の冒頭にヘッダを置く（ルート `CLAUDE.md` 第6節の形式）
2. `work/<案件ID>/audit.md` に根拠を追記する
3. 未確認の法令条番号を条文に使わない
4. 既存規程は本文を読んでから引用する（検索スニペットで引用しない）
5. 判断できないことを断定しない。人間に上げる

# 第2部　スラッシュコマンド（`commands/`）

サブエージェントは互いを呼べないため、**実行順とファイルの受け渡しはすべてコマンドが担う。**

## 1. ファイル形式

```markdown
---
description: このコマンドが何をするか（コマンド一覧に表示される）
argument-hint: <引数の形式>
allowed-tools: Agent, Read, Write, Edit, Glob, Grep, AskUserQuestion, Skill, Bash
---

# コマンド名

対象：$ARGUMENTS
```

## 2. 親エージェントの責務

コマンド本文は**親エージェント（コマンドを実行する Claude 自身）への指示書**。
「サブエージェントに任せて終わり」にしない。

| 責務 | 具体的に |
|---|---|
| 実行順の制御 | どのエージェントを、どの順で、並列か直列かを決める |
| **成果物の検証** | 各フェーズ完了後、**親自身が成果物ファイルを読む**。報告文だけで次に進まない |
| 分岐の判断 | 抵触・不可判定が出たらユーザーに確認する。勝手に進めない |
| ユーザーとの対話 | 承認ゲート、方針確認、アップロードの可否 |
| 案件IDの管理 | 作業ディレクトリの作成とリネーム |

各フェーズに「完了後、**あなた自身が** 〇〇.md の第◯節を読み、〜を確認する」を必ず入れる。
これがないと、サブエージェントの失敗が検出されないまま最後まで流れる。

## 3. 並列実行

依存関係のないエージェントは**1つのメッセージで複数の Agent 呼び出し**を行う。

| 並列にするペア | 理由 |
|---|---|
| `01-legal-research` ‖ `02-consistency` | 外部調査と社内調査。互いに独立 |
| `04-legal-review` ‖ `05-devils-advocate` | **互いの結論に引きずられないよう必ず独立に走らせる** |

④⑤を直列にすると後発が先発に引きずられ、対立が表面化しない。⑥の調停材料が失われる。

## 4. 人間の承認ゲート

**すべての規程作成コマンドに、⑥最終案の後の承認ゲートを入れる。省略不可。**

提示するもの：`06_最終案.md` 第0節サマリ／第4節【経営判断事項】／第6節「確認してほしいこと」
選択肢：承認して次へ進む / 修正指示を出す / 中止する

**【経営判断事項】が残っている場合は、先にそれを決めてもらう。** 未決のまま承認に進ませない。

承認ゲートより後に置くもの：`07-comms`、`09-procedure`、`10-diff-impact`、
docx/pptx/xlsx 生成、OneDrive アップロード。

## 5. OneDrive への書き込み

- **エージェントにアップロード権限を持たせない。** 親がユーザー確認を取ってから実行する
- アップロードは `work/<案件ID>/out/` の中身のみ。**中間成果物は上げない**
- 既存ファイルの削除・リネーム・移動はしない（`settings.json` で deny 済み）
- 改定時、旧版ファイルは残す（効力は附則の廃止条項で処理される）

## 6. 新しいコマンドの骨格

```
1. 案件IDの決定と作業ディレクトリ作成
2. フェーズごとに Agent 呼び出し
   └ 各フェーズ後に「親自身が成果物を読む」検証ステップ
3. 承認ゲート
4. 成果物生成（docx/pptx/xlsx）
5. アップロード（要確認）
6. コミット
7. ユーザーへの報告（成果物一覧・決裁ルート・要確認事項）
```

末尾に「守ること」を置き、親が省略しがちな点を明示的に禁止する。

# 第3部　変更時のチェックリスト

## エージェントを追加・変更したとき

- [ ] `name` とファイル名が一致しているか
- [ ] `description` だけを読んで、親が「いつ呼ぶか」を判断できるか
- [ ] `tools` が最小権限か。**社内文書ツールと外部Webツールを同時に持たせていないか**
- [ ] 「事前に読むもの」に必要なファイルが漏れなく列挙されているか
- [ ] 「出力」の見出し構成が、後続エージェントが読む前提と一致しているか
- [ ] 「やってはいけないこと」が具体的な失敗パターンになっているか
- [ ] 他のエージェントを呼ぶ記述を書いていないか
- [ ] `commands/` 側の記述と矛盾していないか

## コマンドを追加・変更したとき

- [ ] `allowed-tools` に `Agent` が含まれているか
- [ ] 各フェーズに親自身による成果物の検証ステップがあるか
- [ ] ④⑤が並列指定になっているか
- [ ] 承認ゲートがあるか。その後に周知資料・アップロードが来ているか
- [ ] エージェント名が `agents/` の実ファイルと一致しているか
- [ ] 参照している成果物のパス・節番号が、エージェント側の「出力」と一致しているか

## 共通

- [ ] `agents/` `commands/` の直下に `CLAUDE.md` を置いていないか
- [ ] ルート `CLAUDE.md` の格納先・体裁ルールと矛盾していないか

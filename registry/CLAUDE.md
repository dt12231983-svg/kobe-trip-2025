# 現行規程台帳ディレクトリ

`regulations.yaml` は**このシステム全体の土台**。
「現行規程が何であるか」が確定していなければ、整合性チェックも改定も成立しない。

生成・更新は `08-registry`（`/規程-台帳更新` から実行）。

---

## 1. 最重要ルール

### 推測で `current` にしない

同一の正式名称を持つファイルが複数あるとき、**新しい方を選ぶ、という処理をしてはならない。**

`status: current` にしてよいのは次の場合だけ。

- 施行日が明確に異なり、**かつ**新版の附則で旧版の廃止が確認できる

それ以外はすべて `status: 要確認` とし、`candidates:` に候補を全部並べて `question:` に
「何が確認できていないのか」を書く。判断は人間に委ねる。

### `last_verified_by: human` を上書きしない

人間が確定したエントリには次が付く。**`08-registry` はこれを上書きしてはならない。**

```yaml
last_verified_by: human
verified_at: "2026-08-15"
```

台帳を全部作り直す処理を書かない。**差分更新する。**

### ファイル名で判断しない

ファイル名の日付と本文の附則の日付が食い違うことがある。**本文を読む。**
`read_resource` で第1条と附則を確認してから記録する。

## 2. なぜこの台帳が要るのか

OneDrive の現状（2026-08-10 時点で確認）：

| 問題 | 実例 |
|---|---|
| 同名規程の複数版が併存 | コンプライアンス管理規程「（2025.8.1）」「　20260401改訂」 |
| 別バージョンの併存 | 整備管理規程「（20260601）」「（TRC）」 |
| 層をまたぐ併存 | ハラスメント防止規程が EVGM版（2023.1.1）と HD版（20260401制定） |
| 複数フォルダへの重複配置 | 賃金規程が `【閲覧用】規程・就業規則/` と `人事制度/` に |
| 命名ゆれ | `（2024.9.1）` `_20260401施行` `　20260401制定` `(20260401改定)` |
| 原本の所在不明 | 就業規則（イントラには掲載されているが原本ファイル未特定） |

この状態では `02-consistency` が「〇〇規程第5条によれば」と書けない。台帳がその解決手段。

## 4. `regulations.yaml` のスキーマ

```yaml
meta:
  updated_at: "YYYY-MM-DD"
  updated_by: 08-registry | seed
  verified: true | false        # 本文を読んで検証済みか
  source_roots: [...]

regulations:
  - id: <英小文字ケバブ>          # 他エントリからの参照キー。変更しない
    name: <規程名>
    official_name: <本文中のタイトル>   # ファイル名と食い違う場合は両方記録
    layer: HD | EVGM              # 第1条の名宛人から判定
    status: current | superseded | 要確認
    effective_date: "YYYY-MM-DD"
    revision_note: <改定表記>
    parent: <上位規程の id>
    children: [<下位規程の id>]
    owner_dept: <主管部署>
    legal_basis: [<根拠法令>]
    labor_standards_act: true|false   # 労基法上の就業規則に当たるか（09-procedure が使う）
    files:
      - name: <ファイル名>
        root: REG_ROOT | REG_ROOT_PERSONAL | HR_ROOT
        web_url: <URL>
        last_modified: "YYYY-MM-DD"
        role: current | superseded | duplicate
    note: <補足>

    # status: 要確認 の場合のみ
    candidates: [...]
    question: <何が確認できていないか。人間が何を判断すべきか>

    # 人間が確定した場合のみ
    last_verified_by: human
    verified_at: "YYYY-MM-DD"

reference_documents: [...]   # 規程以外（決裁基準表・業務分掌表・書式見本）
issues: {...}                # 検出した不整合
```

### `layer` の判定基準

第1条の名宛人を見る。

- `HD`：「株式会社D&Dホールディングス…及び当社子会社並びに当社関連会社（…「グループ」…）」
- `EVGM`：「株式会社エバーグリーンモビリティ（以下「会社」という。）」

**HD層の規程は EVGM 単独で制定・改廃できない。** この判定が誤ると決裁ルートを間違える。

### `id` は変更しない

`parent` / `children` / `issues` から参照されるため、一度付けた `id` を変えると参照が壊れる。
規程名が変わった場合も `id` は据え置き、`name` だけ変える。

## 5. 現在の状態

`regulations.yaml` は **`meta.verified: false` のシード**。
2026-08-10 に SharePoint 検索で収集したファイル一覧に基づくが、**各規程の本文は未読**で、
検索スニペットからの推定を含む。

**`/規程-台帳更新` を1回実行して検証すること。** 特に以下4件の確定が必要。

1. コンプライアンス管理規程 — 2版のどちらが現行か
2. 整備管理規程 — 「TRC」が何を指すか、20260601版との関係
3. ハラスメント防止規程 — EVGM版とHD版の併存は意図的か
4. 就業規則 — 原本ファイルの所在

---

## 6. やってはいけないこと

- OneDrive 上のファイルを**削除・リネーム・移動する**。台帳整備は読み取りと提案のみ
- `REG_ROOT_PERSONAL`（個人領域）に書き込む
- 版が判別できないものを推測で `current` にする
- `last_verified_by: human` のエントリを上書きする
- 検索結果を途中で打ち切る（`nextOffset` を最後まで辿る）
- 台帳を全部書き直す（差分更新する）
